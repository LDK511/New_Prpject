# 명세: 사용자가 NestJS 마이크로서비스 쇼핑몰에서 회원가입·로그인하고 상품을 주문해 모의 결제로 '결제 완료(테스트)' 상태를 받은 뒤 Redis(BullMQ) 큐로 주문 알림을 받으며, 본인 정보와 주문은 로그인한 사람만 조회할 수 있게 된다.

- 상태: 승인됨
- 날짜: 2026-11-16 00:45
- 요청: 엔터프라이즈급 쇼핑몰을 마이크로서비스로 만들어줘. 회원, 상품, 주문 서비스와 게이트웨이, 알림 워커로 나누어주고, 서비스마다 전용 DB를 써줘. 주문 알림은 Redis 대기열로 처리하고, 회원 정보와 주문은 로그인한 사람만 조회 가능하게 만들어줘.

## 목표
사용자가 NestJS 마이크로서비스 쇼핑몰에서 회원가입·로그인하고 상품을 주문해 모의 결제로 '결제 완료(테스트)' 상태를 받은 뒤 Redis(BullMQ) 큐로 주문 알림을 받으며, 본인 정보와 주문은 로그인한 사람만 조회할 수 있게 된다.

## 범위
- NestJS TypeScript 모노레포(게이트웨이·회원·상품·주문 서비스·알림 워커·모의 결제 서버)
- 서비스별 전용 PostgreSQL DB와 Prisma 스키마·마이그레이션
- 회원가입·로그인 JWT 발급(회원 서비스)과 게이트웨이 토큰 검증·사용자 ID 헤더 전달
- USER/ADMIN 역할: 본인 정보·주문 조회, 관리자 상품 관리·전체 주문 조회
- 상품 목록·상세 조회와 재고 관리
- 주문 생성 시 상품 서비스 동기 재고 예약, 결제 실패·시간 초과 시 예약 해제 보상
- 모의 결제 연동으로 주문 '결제 완료(테스트)' 처리
- BullMQ 주문 알림 큐(지수 백오프 재시도·실패 큐)와 docker-compose 로컬 실행

## 이번에 만들지 않음

- 프론트엔드 웹/앱 화면
- 이메일·SMS·푸시 실제 발송(로그 기록으로 대체)
- 장바구니·쿠폰·리뷰·배송 추적 기능
- Kafka 등 이벤트 소싱·Saga 오케스트레이터 도입
- 쿠버네티스 배포·오토스케일링·서비스 메시
- 소셜 로그인·비밀번호 찾기·2단계 인증
- gRPC·GraphQL API

## 합격 조건

| ID | 종류 | 조건 | 확인 방법 | 자동 확인 |
|---|---|---|---|---|
| AC-1 | 품질 | docker-compose up 한 번으로 게이트웨이·회원·상품·주문 서비스·알림 워커·모의 결제 서버·Redis와 서비스별 PostgreSQL 3개가 뜨고, 각 서비스의 헬스 체크가 200을 반환한다 | docker compose up 후 각 서비스 GET /health → 200 | 확인 불가 |
| AC-2 | 데이터 | 회원·상품·주문 서비스는 각자 별도의 PostgreSQL DB와 Prisma 스키마를 사용하며, 다른 서비스의 DB에 직접 접속하는 코드나 설정이 없다 | 서비스별 DATABASE_URL·schema.prisma 분리 확인, prisma migrate deploy 성공 | 확인 불가 |
| AC-3 | 보안 | 사용자가 이메일·비밀번호로 가입 후 로그인하면 JWT를 받고, 비밀번호는 해시로만 저장되며, 틀린 비밀번호로 로그인하면 401을 받는다 | POST /api/auth/login 잘못된 비밀번호 → 401, DB password 컬럼이 평문이 아님 | 확인 불가 |
| AC-4 | API | 이미 가입된 이메일로 가입하거나 이메일 형식이 틀리면 각각 409와 400을 반환한다 | POST /api/auth/signup 중복 이메일 → 409, 'abc' 이메일 → 400 | 확인 불가 |
| AC-5 | 보안 | 토큰 없이 또는 만료·위조된 토큰으로 회원 정보나 주문을 조회하면 게이트웨이가 401을 반환하고 내부 서비스로 요청을 전달하지 않는다 | GET /api/users/me, GET /api/orders 토큰 없음 → 401 | 확인 불가 |
| AC-6 | 보안 | 외부 클라이언트가 사용자 ID 헤더를 직접 넣어 보내도 게이트웨이가 이를 제거하고 토큰에서 꺼낸 사용자 ID로 덮어쓴다 | 다른 사용자 ID 헤더 + 내 토큰 → 내 정보만 반환 | 확인 불가 |
| AC-7 | 보안 | USER가 다른 사용자의 주문 ID로 조회하면 403(또는 404)을 받고, ADMIN은 전체 주문 목록을 조회할 수 있다 | USER GET /api/orders/{타인주문} → 403, ADMIN GET /api/admin/orders → 200 | 확인 불가 |
| AC-8 | API | USER가 상품 생성·수정·삭제 API를 호출하면 403을 받고, ADMIN은 상품을 등록·수정할 수 있으며 비로그인 사용자도 상품 목록을 조회할 수 있다 | USER POST /api/products → 403, ADMIN → 201, 비로그인 GET /api/products → 200 | 확인 불가 |
| AC-9 | 기능 | 로그인한 사용자가 재고가 충분한 상품을 주문하면 재고가 예약되고 모의 결제 후 주문 상태가 '결제 완료(테스트)'가 되며 재고가 주문 수량만큼 줄어든다 | 재고 10에서 3개 주문 → 201, 주문 상태 PAID_TEST, 상품 재고 7 | 확인 불가 |
| AC-10 | API | 재고보다 많은 수량, 수량 0 이하, 존재하지 않는 상품으로 주문하면 각각 409·400·404를 반환하고 주문과 재고 예약이 생성되지 않는다 | POST /api/orders 수량 999 → 409, 0 → 400, 없는 상품 → 404 | 확인 불가 |
| AC-11 | 데이터 | 모의 결제가 실패하거나 예약 제한 시간이 지나면 주문이 실패/취소 상태가 되고 예약된 재고가 원래 수량으로 돌아온다 | 모의 결제 실패 설정으로 주문 → 주문 FAILED, 재고 원복 | 확인 불가 |
| AC-12 | 데이터 | 동시에 같은 상품을 재고보다 많이 주문해도 재고가 음수가 되지 않는다 | 재고 5에 1개씩 10건 동시 주문 → 성공 5건, 재고 0 | 확인 불가 |
| AC-13 | 기능 | 주문이 결제 완료되면 BullMQ 큐에 알림 작업이 들어가고 알림 워커가 처리해 주문 ID가 담긴 알림 처리 로그를 남긴다 | 주문 후 워커 로그에 주문 ID 알림 처리 기록, 작업 completed | 확인 불가 |
| AC-14 | 기능 | 알림 처리가 계속 실패하면 지수 백오프로 설정된 횟수만큼 재시도한 뒤 작업이 실패 큐에 보관되고, 주문 상태는 바뀌지 않는다 | 워커 강제 실패 → attemptsMade=설정값, failed 상태 작업 존재, 주문 PAID_TEST 유지 | 확인 불가 |
| AC-15 | 품질 | 모든 서비스가 TypeScript 빌드와 린트를 오류 없이 통과하고, 인증·재고 예약·보상 로직 단위 테스트가 통과한다 | npm run build && npm run lint && npm test 종료 코드 0 | 확인 불가 |
