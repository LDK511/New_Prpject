# 명세: 사용자가 게이트웨이 하나를 통해 회원가입·로그인하고 상품을 보고 주문한 뒤 모의 결제를 마치면, 주문 알림 메일을 Redis 대기열(BullMQ)을 거쳐 받을 수 있게 됩니다.

- 상태: 승인됨
- 날짜: 2026-11-15 20:32
- 요청: 엔터프라이즈급 쇼핑몰을 마이크로서비스로 만들어줘. 회원, 상품, 주문 서비스와 게이트웨이, 알림 워커로 나누고, 서비스마다 전용 DB를 써줘. 주문 알림은 Redis 대기열로 처리하고, 회원 정보와 주문 정보는 로그인한 사용자만 조회할 수 있게 만들어줘.

## 목표
사용자가 게이트웨이 하나를 통해 회원가입·로그인하고 상품을 보고 주문한 뒤 모의 결제를 마치면, 주문 알림 메일을 Redis 대기열(BullMQ)을 거쳐 받을 수 있게 됩니다.

## 범위
- NestJS 모노레포: 게이트웨이·회원·상품·주문 서비스, 알림 워커
- 서비스별 독립 PostgreSQL과 Prisma schema·마이그레이션
- 회원가입·로그인 JWT 발급(role 포함)과 게이트웨이 JWT 검증
- 상품 목록·상세 조회, ADMIN 전용 상품 등록
- 주문 생성 시 재고 예약, 결제 확정·실패·만료 시 보상 해제(오케스트레이션 사가)
- 모의 결제 서버와 결제 완료(테스트) 웹훅 처리
- BullMQ 주문 알림 큐: 지수 백오프 재시도, 실패 큐, 메일 발송
- docker compose 로컬 일괄 실행

## 이번에 만들지 않음
- 실제 Stripe 키를 쓰는 실결제와 환불
- 프론트엔드 웹/앱 화면
- 장바구니·쿠폰·리뷰·검색 기능
- SMS·푸시 알림 채널
- 쿠버네티스 배포·오토스케일링·서비스 메시
- 소셜 로그인과 비밀번호 재설정
- 관리자 대시보드 UI

## 합격 조건

| ID | 종류 | 조건 | 확인 방법 | 자동 확인 |
|---|---|---|---|---|
| AC-1 | 품질 | docker compose up 한 번으로 게이트웨이·회원·상품·주문·알림 워커·모의 결제 서버·Redis와 PostgreSQL 3개가 뜨고, 각 서비스 헬스체크가 200을 반환한다 | compose up 후 각 서비스 GET /health → 200 | 아직 없음 |
| AC-2 | 데이터 | 회원·상품·주문 서비스는 각자 별도 PostgreSQL DB만 사용하며, Prisma Migrate로 스키마가 생성되고 다른 서비스 DB에는 접속하지 않는다 | 각 서비스 DATABASE_URL이 서로 다름, prisma migrate deploy 성공 | 아직 없음 |
| AC-3 | API | 회원가입 후 로그인하면 사용자 ID와 role이 담긴 JWT를 받고, 비밀번호가 틀리면 401을, 이미 가입된 이메일로 가입하면 409를 받는다 | POST /auth/login 정상 → 200+토큰, 오답 → 401, 중복 가입 → 409 | 아직 없음 |
| AC-4 | 보안 | 비밀번호는 bcrypt 등 해시로만 저장되고 API 응답에 비밀번호·해시가 포함되지 않는다 | users 테이블 평문 없음, GET /users/me 응답에 password 필드 없음 | 아직 없음 |
| AC-5 | 보안 | 토큰 없이 또는 만료·위조된 토큰으로 회원 정보나 주문 조회를 요청하면 게이트웨이가 401을 반환하고 하위 서비스로 요청을 넘기지 않는다 | Authorization 없이 GET /users/me, GET /orders → 401 | 아직 없음 |
| AC-6 | 보안 | 게이트웨이는 클라이언트가 직접 보낸 사용자 ID 헤더를 지우고, 검증된 JWT의 사용자 ID·role로만 헤더를 다시 채워 전달한다 | x-user-id 위조 헤더+정상 토큰 → 본인 데이터만 반환 | 아직 없음 |
| AC-7 | 보안 | 로그인한 사용자가 다른 사용자의 주문 ID로 조회하면 403을 받고, 주문이 하나도 없으면 빈 배열과 200을 받는다 | 타인 GET /orders/:id → 403, 신규 회원 GET /orders → [] | 아직 없음 |
| AC-8 | API | 누구나 상품 목록·상세를 조회할 수 있고, ADMIN은 상품을 등록할 수 있으며 USER가 등록하면 403, 가격이 음수이거나 이름이 비면 400을 받는다 | USER POST /products → 403, ADMIN 가격 -1 → 400 | 아직 없음 |
| AC-9 | 기능 | 주문을 만들면 재고가 예약되고 주문은 결제 대기 상태가 되며, 재고보다 많은 수량을 주문하면 409를 받고 재고는 바뀌지 않는다 | 재고 5에 수량 6 주문 → 409, 재고 5 유지 | 아직 없음 |
| AC-10 | 데이터 | 모의 결제 성공 웹훅을 받으면 주문이 '결제 완료(테스트)'가 되고 예약 재고가 확정되며, 같은 웹훅을 다시 받아도 재고가 두 번 차감되지 않는다 | 웹훅 2회 전송 후 재고 차감 1회, 주문 상태 PAID_TEST | 아직 없음 |
| AC-11 | 기능 | 결제가 실패하거나 예약 만료 시간이 지나면 주문이 취소되고 예약했던 재고 수량이 원래대로 돌아온다 | 실패 웹훅 또는 만료 후 주문 CANCELLED, 재고 원복 | 아직 없음 |
| AC-12 | 기능 | 결제가 완료되면 Redis 이벤트로 BullMQ 알림 잡이 등록되고, 워커가 주문자 이메일로 주문 완료 메일을 보낸다 | 결제 후 MailHog 등 테스트 SMTP에 메일 1건 도착 | 아직 없음 |
| AC-13 | 품질 | 메일 발송이 실패하면 지수 백오프로 정해진 횟수만큼 다시 시도하고, 모두 실패한 잡은 실패 큐에 남으며 주문 상태는 바뀌지 않는다 | SMTP 중지 후 결제 → 재시도 로그, failed 큐에 잡 1건 | 아직 없음 |
| AC-14 | 보안 | 모의 결제 웹훅 서명 값이 틀리거나 빠진 요청은 400을 받고 주문 상태가 바뀌지 않는다 | 서명 누락 웹훅 → 400, 주문 PENDING 유지 | 아직 없음 |

> 합격 조건은 사람이 확인·승인한 완성 기준입니다. 자동 확인(테스트) 결과는 아직 연결되지 않았습니다.
