# ADR-004: 서비스 간 통신과 게이트웨이 API 형태는 어떻게 할까요?

- 상태: 승인됨
- 날짜: 2026-11-15
- 요청: 엔터프라이즈급 쇼핑몰을 마이크로서비스로 만들어줘. 회원, 상품, 주문 서비스와 게이트웨이, 알림 워커로 나누고, 서비스마다 전용 DB를 써줘. 주문 알림은 Redis 대기열로 처리하고, 회원 정보와 주문 정보는 로그인한 사용자만 조회할 수 있게 만들어줘.

## 결정
**REST 동기 + Redis 이벤트 혼합** — 게이트웨이는 REST 라우팅, 상태 변경 전파는 이벤트로 처리

근거(장점):
- 조회는 단순하고 변경 전파는 느슨하게 결합
- 알림 큐와 인프라 공유

## 검토한 대안
- REST 동기 호출만 사용 (모든 서비스 간 호출을 HTTP/JSON으로 처리) → 장애가 연쇄적으로 전파되고 결합도가 높음 이유로 제외
- 내부 gRPC + 게이트웨이 REST (내부는 gRPC/Protobuf, 외부에는 REST 제공) → proto 관리와 디버깅 부담 이유로 제외
- GraphQL 게이트웨이 집계 (게이트웨이가 GraphQL로 여러 서비스 데이터를 집계) → 스키마·N+1 문제 관리 등 복잡도 증가 이유로 제외

## 영향
서비스 간 결합도·장애 전파·API 계약 설계 · 감수: 두 가지 통신 방식을 함께 운영해야 함
