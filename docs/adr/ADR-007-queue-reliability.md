# ADR-007: Redis 대기열 기반 주문 알림의 구현 방식과 신뢰성 정책은 어떻게 할까요?

- 상태: 승인됨
- 날짜: 2026-11-15
- 요청: 엔터프라이즈급 쇼핑몰을 마이크로서비스로 만들어줘. 회원, 상품, 주문 서비스와 게이트웨이, 알림 워커로 나누고, 서비스마다 전용 DB를 써줘. 주문 알림은 Redis 대기열로 처리하고, 회원 정보와 주문 정보는 로그인한 사용자만 조회할 수 있게 만들어줘.

## 결정
**BullMQ + 지수 백오프 재시도 + 실패 큐** — BullMQ 잡 큐로 재시도·실패 보관, 메일(SMTP/SES) 우선 발송

근거(장점):
- 재시도·지연·모니터링 기본 제공
- Node 생태계와 궁합 좋음

## 검토한 대안
- Redis Streams + 컨슈머 그룹 (XADD/XREADGROUP으로 직접 구현, ACK·PEL 기반 재처리) → 재시도·DLQ 로직 직접 구현 필요 이유로 제외
- Redis List(LPUSH/BRPOP) 단순 큐 (최소 구현, 실패 시 로그만 남김) → 워커 장애 시 메시지 유실 위험 이유로 제외
- 트랜잭셔널 아웃박스 + BullMQ, 메일·문자 병행 (주문 DB 아웃박스에서 큐로 발행, 멱등키로 중복 방지) → 구성 복잡도·문자 발송 비용 증가 이유로 제외

## 영향
알림 워커 구조·메시지 유실/중복 처리·외부 발송 연동 · 감수: Node.js 전용 라이브러리
